# Industry research — serving, isolation, and token unit economics

This file records only pages opened for this review. Hardware tokens/sec appear only with the source’s conditions. Case-pack constants from `rel-m04-l03` (149, 58, 280, 90 seconds, 21 SAR) are planning fiction, not benchmarks.

## Prefill and decode are different jobs

Autoregressive serving has two phases. Prefill (context) runs the prompt and writes the KV cache. Decode (generation) then emits one token at a time and reads that cache. A long referral letter is prefill-heavy. A chat turn that has already started is decode-heavy. They contend for the same GPU, and they do not want the same batch shape.

TensorRT-LLM’s scheduler page states the operational consequence: sequences in the context phase can be processed together with sequences in the generation phase, and “padding sequences in the generation phase that contain a single token to the length of the maximum input sequence is inefficient.” The same page says `max_num_tokens` should be high enough for GPU math utilization and not so high that time to first token (TTFT) and time per output token (TPOT) miss their SLOs. Default `max_num_tokens` is 8192 starting from TensorRT-LLM v0.11, and NVIDIA says to tune it. Those are configuration facts, not a throughput claim.

vLLM’s 5 September 2025 engine anatomy describes the same split inside one step. The scheduler prefers running (decode) requests, then admits waiting (prefill) requests while a token budget remains. If the pool cannot allocate blocks, the engine may recompute-preempt by evicting low-priority requests, or skip the admission. Swap of KV cache to CPU is described as a V0 behavior; the V1 user guide lists “GPU <> CPU KV Cache Swapping” as deprecated. Teaching “page the cache to RAM and you have solved the surge” is behind the engine the project documents in 2025.

Chunked prefill exists so one long prompt cannot occupy the step. The anatomy post says a prompt is split into chunks (its example uses 8 tokens per chunk) and a new token is sampled only on the last chunk. The V1 user guide says the unified scheduler tracks `{request_id: num_tokens}` and uses that budget for chunked prefill, prefix caching, and speculative decoding without a hard wall between phases. TensorRT-LLM’s name for the same idea is chunked context: chunks interleave with generation, TTFT becomes more stable, and a few short prompts that used to finish in one iteration can get slower. That tradeoff belongs in the lesson. A single “batched tokens per second” hides it.

## KV cache is the capacity unit

The June 2023 vLLM blog (Kwon, Li, and coauthors) is the primary description of PagedAttention this review uses. Conditions they state: LLaMA-7B on one NVIDIA A10G, and LLaMA-13B on one NVIDIA A100 40GB; request lengths sampled from ShareGPT. Under those conditions they report up to 24× the throughput of Hugging Face Transformers and up to 3.5× Hugging Face Text Generation Inference (the 3.5× figure is for three parallel completions; single-completion comparisons in the same post are 2.2×–2.5× versus TGI and 14×–24× versus HF). They also report that the KV cache for one LLaMA-13B sequence takes up to 1.7GB, that existing allocators wasted 60–80% of memory to fragmentation and over-reservation, and that paging waste is the last block only, “under 4%” in their practice. Parallel sampling shared blocks via copy-on-write, cutting memory up to 55% and raising throughput up to 2.2× in that setting. These multiples are not transferable to `local-small` on the cluster’s one GPU. They do establish the mechanism: capacity is how many KV blocks you can pack, not a nameplate tokens/sec.

The 2025 anatomy post says each block stores 16 tokens by default, so a 17-token prefill needs two blocks. Logical tokens map to non-contiguous physical blocks. Continuous batching then flattens the step into one sequence with masks, so mixed lengths do not need right-padding. The historical kernel note at `docs.vllm.ai` (`design/paged_attention`) warns that it “no longer describes the code used in vLLM today.” Kernel layout is unstable; the block table is the idea to teach.

Anyscale’s 22 June 2023 measurements (Cade Daniel, Chen Shen, Eric Liang, Richard Liaw) are the continuous-batching numbers worth quoting, because the conditions are explicit. One NVIDIA A100 40GB. Meta OPT-13B in a build that fits without tensor parallelism. Throughput: 1,000 requests, 512 input tokens each, generation lengths drawn from an exponential with mean 128 and then capped at 32, 128, 512, or 1,536; end-of-sequence ignored so the cap is honored. They report up to 23× throughput versus naive static batching when vLLM’s continuous batching and its memory allocator are both in use; about 8× from continuous batching alone on Ray Serve and on Hugging Face text-generation-inference; about 4× from FasterTransformer’s kernels on static batching. At the high-variance cap (1,536 new tokens) they say naive static batching falls to 81 tokens/s. They do not publish, on the page fetched here, the matching absolute tokens/s for vLLM, so this review does not invent one. Latency curves use 100 prompts with input lengths uniform from 1 to 512 and outputs capped at 1,536, at 1 and 4 queries per second. Their qualitative result matters more than the multiple: once the GPU is full, new requests wait, and a system with a larger effective batch (vLLM, in their plot) holds latency longer as QPS rises. That is the surge. Static batching wastes the GPU when lengths differ, which is why the lesson’s unbatched-versus-batched switch is the right story and the wrong model. Orca (OSDI 2022) is the system Anyscale credits for iteration-level scheduling. This review did not re-read the OSDI paper; the scheduling claim is taken from Anyscale’s account of it.

## Four serving alternatives

### 1. vLLM — Proven for the private-cloud path

vLLM’s current overview lists PagedAttention, continuous batching, chunked prefill, prefix caching, quantization, and disaggregated prefill/decode/encode. Disaggregation is listed as a feature of the project in 2026; this review did not open a production case study of disaggregation on a two-GPU hospital cluster, so treat “split prefill and decode onto different GPUs” as **Emerging** relative to a one-GPU case (`gpus: 1` in the forecast). The core scheduler is **Proven**.

Admission is a policy, not a slogan. Stable scheduler docs define `fcfs` (arrival order) and `priority` (lower numeric priority runs first; arrival time breaks ties). The anatomy narrative’s English phrase “higher priority” must not be taught as “larger integer.” The integer convention in the API docs is the one to grade. When blocks run out, low-priority work is the eviction candidate. That is how chat keeps a reserve: give chat the better priority and refuse to evict it to admit backlog prefill.

Multi-LoRA on one process is documented, not hypothetical. `vllm serve … --enable-lora --lora-modules name=path` publishes each adapter as its own model id. Requests name the adapter in the `model` field and run beside the base and beside other adapters when `max_loras` allows it. `--max-lora-rank` is set to the largest rank you will load; the docs say a much larger rank wastes memory. Dynamic add/remove requires `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True`, and the same page warns that this “should not be used in production unless it is an isolated, fully trusted environment.” The lesson’s unregistered candidate is exactly that warning. Loading a hash because the shell name looks close is the supply-chain failure Module 4 Lesson 1 already named (`atk-supply`). Serving time is when the register is enforced.

CUDA graph capture is part of cold start. Unless `--enforce-eager` is set, engine init runs dummy batches and captures graphs. A pod can be “Running” while that capture is unfinished. The lesson’s 90-second constant is a case knob. The mechanism to teach is “ready for inference is later than process start,” which includes weight load and graph capture. This review did not find a portable seconds figure for that gap, and does not invent one.

### 2. SGLang — Proven runtime, Emerging reason to prefer it

SGLang’s docs (HiCache design, session radix cache, FAQ, and the TPU feature matrix as a statement of intended features) describe RadixAttention: a radix tree of token prefixes to paged KV, LRU eviction of leaves whose reference count is zero, and a cache-aware scheduler that would rather continue a shared prefix than thrash. The LMSYS post of 17 January 2024 (Zheng, Yin, Xie, and coauthors) is the benchmark this review will cite. Conditions: Llama-7B, FP16, tensor parallelism 1, one A10G (they state 24GB); and Mixtral-8x7B, FP16, tensor parallelism 8, eight A10G GPUs. Baselines: vLLM 0.2.5, Guidance 0.1.8, TGI 1.3.0. Workloads include MMLU 5-shot, HellaSwag 20-shot, ReAct traces, a tree-of-thought GSM8K prompt, JSON extraction, 4-turn chat, a DSPy RAG tutorial, and LLaVA. They report up to 5× throughput versus those baselines on those workloads, and they attribute gains to prefix reuse, intra-program parallelism, and frontend/backend co-design. An ablation they describe showed little overhead when nothing hit, so they leave the cache on. That 5× is not a 2026 claim that SGLang beats current vLLM on a referral batch with no shared prefix. A campaign of distinct referral letters may barely hit. A public hours question, a shared system prompt, and a multi-turn chat will hit. The lesson should pick SGLang when the traffic is prefix-heavy, and vLLM when the win is packing a mixed batch. Both are legitimate. “SGLang is faster” is not.

HiCache (documented on docs.sglang.io) extends the tree to GPU (L1), host (L2), and a distributed L3. Session-aware radix cache prefers evicting unreferenced KV before KV a live session still names, and the doc is explicit that session references are soft: under enough pressure the referenced KV can still go. That is the right caveat for a chat reserve. A pin that is not a pin will not save the SLO.

The FAQ records a production footgun: dynamic batching and prefix caching change which kernel runs, so temperature 0 is not bit-stable. Deterministic mode exists (`--enable-deterministic-inference`); the FAQ points at a September 2025 LMSYS post this review did not re-open. Clinical extraction that must match a gold string cannot ignore this. **Proven** that the effect exists. **Emerging** as a default to turn on without measuring quality.

The TPU matrix lists multi-LoRA as in development on that backend. Do not tell students SGLang multi-LoRA is equivalent to vLLM’s on every device. The English localization mirror that claims “400,000 GPUs” was not used; this review did not confirm that figure on docs.sglang.io.

### 3. TensorRT-LLM on Triton — Proven where an engine is prebuilt

Triton’s TensorRT-LLM backend exists to serve those engines with inflight batching and paged attention. Model config sets `batching_strategy: inflight_fused_batching` (or `V1` to disable it). Triton documents that the runtime batch can exceed `triton_max_batch_size` because the TRT-LLM scheduler applies `max_num_tokens` and `max_batch_size`. `max_queue_size` rejects when the queue is full. That reject is admission control with a name. `max_queue_delay_microseconds` waits in the hope of filling an iteration. Waiting on purpose is the opposite of the lesson’s “reactive is always late,” and it is sometimes right for throughput. Teach the knob.

Triton’s own batcher page separates classic dynamic batching (stateless, wait for a batch) from iterative sequences, which reschedule still-running requests every step so a finished request’s slot is reused. The page marks iterative sequences as provisional. Prefer the TensorRT-LLM inflight path, which is the supported LLM mechanism, over the provisional sequence-batcher flag.

LoRA on that backend is also documented: weights land in a host cache, move to a GPU cache when scheduled, and later requests send `lora_task_id` only. The inflight batcher can mix adapters in one batch. That is the “three adapters, one process” line the trace promised and the Python list did not implement.

Cost of this option: `trtllm-build` chooses `max_batch_size`, `max_seq_len`, and `max_num_tokens` before serving. A self-paced student without a GPU cannot build an engine. Triton is the right production alternative to name, and a poor core-path dependency. **Proven** as a serving stack. **Experimental** as a required lab.

### 4. A managed API — Proven meter, wrong home for the backlog

NVIDIA NIM, on the current LLM/VLM overview, packages one open-source engine per image, vLLM or SGLang, behind a shared startup and an OpenAI-compatible API. The profile prefix (`vllm-` or `sglang-`) names the engine. The orchestration layer can inject LoRA. An older introduction page (the copy fetched still describes TRT-LLM, vLLM, “or others,” and a multi-LLM versus model-specific container split) is not the same document as the current overview. Teach NIM as a distribution and a support boundary, not as a fourth scheduler. **Proven** product. **Emerging** as something this course should operate: the student still has to know which engine is inside, because the surge behavior is the engine’s.

`ext-large` in the case is the managed API that is not inside the hospital. It is the correct place for public text that the DPO already allowed, and the wrong place for phi rows. Speed is a real temptation. In the pack, 280 tokens/s clears 48 hours and 149 tokens/s also clears, while 58 does not. A managed endpoint can look like that on a given day and still be the wrong contract tomorrow, because the price is theirs and the residency rule is yours.

What to meter, from sources opened here:

- OpenAI’s token-counting help page separates input (prompt), output (completion), cached input, and reasoning tokens. Reasoning tokens are billed as output even when the visible answer is short.
- OpenAI’s prompt-caching guide: caching is prefix reuse. For GPT-5.6 and later, a 30-minute cache write is priced at 1.25× uncached input and a 12-hour write at 2.5×; reads are 0.1× ordinary input on most of those models and 0.05× on GPT-6.1 Sol and GPT-6.1 Terra. The write rate replaces the input rate for those tokens; it is not a second fee. Prices on that page move. The lesson should load a dated sheet. The case already does that for one SAR figure and does not do it for cache or tools.
- OpenAI’s pricing page meters tools apart from tokens. Web search is listed at $10.00 per 1,000 calls plus search-content tokens at model rates. File search tool calls are $2.50 per 1,000 on the Responses API, plus storage. A referral agent that calls a tool on every letter can dominate SAR while the token line looks calm.
- FinOps Foundation’s FOCUS 1.5 scope (page opened for this review) recommends `TokenDirection` (`Input` or `Output`) and `TokenCacheAction` (`Uncached`, `Read`, `Write`, `Other`) on SKU price details. Inclusion is recommended, not required. Reasoning tokens metered apart carry `Output`. A meter that mixes directions omits the property that would lie. The FinOps for AI overview says FOCUS 1.5 was scheduled for ratification in December 2026. Today in this review is 30 October 2026, so treat the column names as **Emerging** standardization, not as a schema the hospital already exports. The same overview’s KPI list (cost per inference, cost per million tokens, cost per successful outcome) is the finance interview. The GenAI token-pricing working-group page states the qualitative fact the case needs: output tokens often cost more than input because generation is the expensive phase, and a cache that is written and not reread can lose money. It says “often three to five times” for output versus input. That is their generalization, not a measurement of `ext-large`. Do not hard-code 5× into the simulator as if it were the vendor’s tariff. Put input, output, cache read, cache write, and tool-call price on the release sheet.

The lesson’s single `sar` per 1,000 tokens flattens all five meters into one. A batch of 1,000-token referral letters is almost all input if the extract is a short JSON, and almost all output if the model writes a long summary. Which one it is changes the bill more than the 21-versus-yesterday story. The price change still matters. It is not the whole bill.

## Isolation is not admission control

NVIDIA’s MIG user guide (introduction and deployment considerations, pages opened here): from Ampere onward, MIG can partition a GPU into as many as seven instances. Each instance gets its own path through crossbar, L2, memory controllers, and DRAM, so a neighbor thrashing its cache does not take your bandwidth. Faults are isolated. That is the multi-tenant story CSPs use.

Limits that make MIG the wrong default for this surge, from the same deployment page:

- Graphics APIs are unsupported, except specified profiles on RTX PRO 6000 Blackwell.
- With driver R570, peer-to-peer works between MIG instances on the same GPU only. Cross-GPU P2P and MIG-to-non-MIG P2P are not supported.
- CUDA IPC does not work across GPU instances (it does across compute instances).
- NCCL is not supported with MIG.
- Enabling MIG on A100/A30 requires a GPU reset and super-user. Daemons holding the device, including DCGM, must stop. Mode persists across reboot until toggled.
- Profiling of shared GPU resources is unsupported.

Amazon’s EKS MIG page, which cites that guide, adds a sizing warning: a `1g` slice is not a proportional share of whole-GPU throughput, because bandwidth and cache differ by profile. Time-slicing does not further split a MIG instance. Changing the layout reboots the node when a reset is required.

**Proven:** MIG when several tenants must be hardware-isolated and each slice can hold its model. **Experimental** as the fix for chat versus batch on the case’s single GPU. The model may not fit the slice, NCCL is unavailable, and the slice cannot be reshuffled at 20:58 without a reset. Inside one engine, priority and a KV reserve are the **Proven** control. Put MIG next to lesson 4’s two sites.

## What this means for the letter night

The backlog is many prefills, short extracts, three LoRA ids, a 5× chat peak, a public prefix, and a cold replica. Static batching waits on the longest letter. Continuous batching with a reserve keeps chat decode moving. A radix cache helps the hours answer and helps the letters only where they share a header. A managed API can finish sooner, itemizes input, output, cache, and tool calls, and is forbidden for phi. A MIG slice that cannot hold the model fails closed. None of that is a cell in `throughput.json`.

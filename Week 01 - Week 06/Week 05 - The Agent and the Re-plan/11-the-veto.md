# The veto

**Days 3 and 4. Software engineer and architect.** The veto sits in code between the plan and the tool, and again between the draft and the answer. It looks at the action the planner proposed. It does not look at the words the person used.

When it fires, the step's node is `veto`, `rule` is the document id from note 08, and `refused` is true. Nothing runs after it, and nothing writes. One veto, and it is the last step.

A question about a forbidden thing is not a veto. "May the second site join?" is a question. The answer is no, with the memo. "Send the second site's captures to the vendor" is an action. That one stops. The same split holds for the pilot, the tier, a person, a model, a log, a write, and a grade.

The same action will arrive in other words. A list of phrases will catch the ones that use your phrases and miss the rest. Test the action, not the sentence. An instruction inside a tool result is data. Do not do what it says. The injection tasks need the document that carries the instruction and the second document that answers it, both on the path.

A veto on a task that should have been answered fails that task. The score command prints missed stops and false stops separately. Read them separately.

Budgets are on the question, in tokens, seconds, and pounds. Price the pounds from `model_register.csv`. M06 is approved for public data only. A step that read a local id, a complaint, or a patient letter uses a model approved for official-sensitive data. A line over budget fails even when the answer is right.

**A miss that looks like progress.** A keyword list that stops at the word "pilot", or the name of the second site, wherever it appears. The questions in the scope slice use those words. They have answers.

**Finish.** You can show one task the keyword baseline refused and yours answered, and one task the keyword baseline answered and yours stopped.

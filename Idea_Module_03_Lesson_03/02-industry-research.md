# Industry research

The sources below were opened for this review. Numbers appear only when the source stated them, and they keep that source’s metric. Nothing here is an nDCG for the Al-Waha pack. The pack has never been scored that way, and a fifteen-document policy register would not support a stable ranked-list score.

## Lexical plus vector, fused by rank

**Proven.** Reciprocal rank fusion was published by Gordon V. Cormack, Charles L. A. Clarke, and Stefan Büttcher at SIGIR 2009. The paper’s abstract states that RRF, a simple method for combining document rankings from multiple IR systems, yielded better results than any individual system in their trials and better results than Condorcet Fuse. They combined TREC submissions and also used RRF as a meta-learner on LETOR 3. A pilot on Wumpus configurations found k = 60 near-optimal and the choice not critical. Across the pilot and the TREC sets they report, RRF outperformed Condorcet, CombMNZ, and the best individual system by about 4 to 5 percent on average mean average precision, with a sign test they present as significant. The author PDF is https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf and the ACM record is https://dl.acm.org/doi/10.1145/1571941.1572114.

The property that matters for this lesson is that RRF uses ranks, so a BM25 score and a cosine do not have to share a scale. Adding 1 to a cosine, which is what `search.rank` does when a code matches, is a score boost. It assumes the cosine cannot reach 1 in a way that changes the decision, and it assumes the code match is worth more than any amount of token overlap. Those assumptions hold for the planted hours pair. They are not fusion.

OpenSearch’s current hybrid-search documents describe the same split. Hybrid search combines a keyword clause and a semantic clause through a search pipeline. The score-ranker processor, introduced in 2.19, implements RRF: the score of a document is the sum, over query clauses in which it appears, of 1 / (k + rank), with rank starting at 1. The default rank constant is 60, the value Cormack’s pilot liked, and the legal range they document is 1 to 10000. A normalization processor, available since 2.10, instead rescales raw scores and combines them. OpenSearch’s own guidance is to start with RRF when the clauses are on incomparable scales or the score distribution is unstable. Primary pages: https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/ and https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/.

The pgvector README’s hybrid section says to use the extension together with Postgres full-text search, links the Postgres text-search introduction at https://www.postgresql.org/docs/current/textsearch-intro.html, and shows a `ts_rank_cd` query. It then points at a Python example for reciprocal rank fusion and another for a cross-encoder: https://github.com/pgvector/pgvector/blob/master/README.md and https://github.com/pgvector/pgvector-python/blob/master/examples/hybrid_search/rrf.py. The README example that is inline is the lexical query. The fusion lives in the linked example. That is the right teaching order for this lesson too: a lexical rank, a second rank, then a fusion the reader can see, with a database left as the place those ranks go when the store outgrows a list.

Anthropic’s contextual-retrieval post, below, treats embeddings plus BM25 plus rank fusion as the ordinary baseline, and then adds chunk context on top. Their first summary finding is that embeddings plus BM25 beat embeddings alone, on their data, under their metric. That finding agrees with the 2009 reason to fuse. It does not make the lesson’s status filter into BM25.

## Permission as a filter on the query, not a check on the winner

**Proven** as a requirement, and uneven in how engines compose it with hybrid queries. OpenSearch document-level security decides which documents a role may retrieve on read. The rule is an OpenSearch query. Their documentation’s example is a Boolean query that requires a field match, and they state that DLS does not restrict writes: a role that can index can still write a document the same role cannot later read. Multiple DLS roles are combined with OR, with an exception when a DLS role is combined with a role that has no DLS. Page: https://docs.opensearch.org/latest/security/access-control/document-level-security/.

Hybrid search has a separate pre-filter. The hybrid query’s top-level `filter` is applied to each subquery, so only documents that match are scored. OpenSearch documents this as introduced in 3.0, and contrasts it with a post-filter that runs after scoring and is aimed at faceted display. Page: https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/pre-filtering/. The hybrid query is specified as a top-level query. Nesting it under wrappers such as `function_score` is documented as unsupported. https://docs.opensearch.org/latest/query-dsl/compound/hybrid/.

Those two features do not automatically compose. OpenSearch issue 1303, “Hybrid Search not working with Document Level Security,” reports that a hybrid query fails when the caller is an internal user whose role has a DLS filter. A comment on that issue states that the failure was still present in OpenSearch 3.2.0 and that a hybrid query with a single `query_string` clause failed the same way under DLS. https://github.com/opensearch-project/neural-search/issues/1303. The self-paced implementation should pre-filter in the same function that builds the candidate list, and should test that list, so the guarantee does not depend on an engine interaction the class has not installed.

The lesson’s `filter.allow` is the right rule for three askers. It runs after `rank` on the non-specialty path, and after `criteria` on the specialty path. A pre-filter would run before either score. The unauthorized circular is the example that shows an audience filter is the wrong single gate: its audience is public. Status, audience, and the version window are three predicates. Fusion is a fourth step, and only on the rows that survive.

## Contextual retrieval

**Emerging.** Anthropic’s engineering post “Introducing Contextual Retrieval,” published 19 September 2024, was still public at https://www.anthropic.com/engineering/contextual-retrieval when this review fetched it. A second URL, https://www.anthropic.com/research/contextual-retrieval, serves the same post. The method prepends a short, chunk-specific context, generated by a model that sees the whole document, to the chunk before the embedding is computed and before the BM25 index is built. They describe the context as usually 50 to 100 tokens. The prompt they print asks for a succinct situating context and nothing else. They say prompt caching is what makes the preprocessing cheap on Claude, and they give a worked cost of $1.02 per million document tokens under a stated assumption (800-token chunks, 8k-token documents, 50 tokens of instruction, 100 tokens of context). That cost is theirs, for that assumption, at the prices they used. It is not a price for this course.

Their metric is one minus recall at 20: the fraction of relevant chunks missing from the top 20. They average across domains with Gemini Text 004 as the top embedding configuration they graph. They report:

- Contextual embeddings reduced the top-20 failure rate by 35 percent, from 5.7 percent to 3.7 percent.
- Contextual embeddings plus contextual BM25 reduced it by 49 percent, from 5.7 percent to 2.9 percent.
- The same pair plus a Cohere reranker, retrieving 150 chunks and then keeping 20, reduced it by 67 percent, from 5.7 percent to 1.9 percent.

They also say generic document summaries on chunks gave very limited gains in their trials, and that hypothetical document embeddings and summary-based indexing performed poorly when they evaluated them. They say passing 20 chunks beat passing 10 or 5 on their sets, and they cite the risk that more context distracts the model. The post is a vendor benchmark, not a peer-reviewed paper. The cookbook repeats the method: https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide.

Two sentences in the same post decide the lesson. First, if the knowledge base is under about 200,000 tokens, they say to put the whole base in the prompt and skip RAG; prompt caching is their cost argument. The `rel-m03-l03` store is far under that size, so a contextual-retrieval project would be practicing a scaling method on a corpus the method’s authors would not yet retrieve. Second, the failure they target is a chunk that says “the company’s revenue grew by 3 percent” and does not name the company. The Al-Waha failure is a chunk that names the right hours and is unauthorized, or a chunk that is the right specialty and the wrong version. Prepended context can make a short clause easier to find. It does not decide `in_force`, audience, or the start-day window. If the contextualizer runs on the unauthorized circular, the extra context can make that circular easier to retrieve. Context is an indexing feature. Permission is a filter.

**Proven** related finding, different paper: stuffing many chunks into the prompt has a position failure. Liu, Lin, Hewitt, Paranjape, Bevilacqua, Petroni, and Liang, “Lost in the Middle,” Transactions of the Association for Computational Linguistics, volume 12, pages 157–173, 2024, DOI 10.1162/tacl_a_00638, preprint https://arxiv.org/abs/2307.03172. They study multi-document question answering and key-value retrieval. Performance is often highest when the relevant information is at the beginning or the end of the context, and it degrades when the relevant information is in the middle, including for models billed as long-context. They report a U-shaped curve. One figure they state in prose: when the relevant information is placed in the middle, GPT-3.5-Turbo’s multi-document question performance is lower than its closed-book performance, and they give the closed-book figure as 56.1 percent. This review does not import any other accuracy from that paper. Anthropic’s choice to pass 20 chunks, and GraphRAG’s appendix note that an 8k context beat larger windows on their comprehensiveness comparisons, both sit next to this result. For the lesson, the implication is narrow. The citation should carry the one clause that bound, not a pile of near neighbors. Lost-in-the-middle is the reason. Re-running the paper is out of scope.

## GraphRAG

**Emerging** for global questions, **Experimental** as this lesson’s index. Darren Edge and colleagues, “From Local to Global: A Graph RAG Approach to Query-Focused Summarization,” arXiv:2404.16130, submitted 24 April 2024, revised 19 February 2025. https://arxiv.org/abs/2404.16130. The Microsoft Research project page lists the preprint: https://www.microsoft.com/en-us/research/project/graphrag/publications/. The open-source docs are https://microsoft.github.io/graphrag/get_started/ and the repository linked from the paper is https://github.com/microsoft/graphrag.

The paper’s claim is that ordinary RAG fails on questions aimed at an entire corpus, such as the main themes of a collection, because those questions are query-focused summarization rather than a lookup. GraphRAG uses a model to extract an entity graph, partitions it into communities, and pregenerates community summaries. A global question is answered by mapping the question over summaries and reducing the partial answers. The getting-started page shows a global query for themes and a local query for a character. The docs warn that indexing can consume a lot of model calls and tell the reader to start on the tutorial set.

Their evaluation, in the v2 HTML, uses LLM-as-judge win rates on comprehensiveness and diversity, plus a directness control, over podcast transcripts and news articles, for a class of global sensemaking questions they describe as living in the one-million-token range. They report that global approaches beat a vector-RAG baseline on comprehensiveness at win rates of 72–83 percent on the podcast set and 72–80 percent on the news set, and on diversity at 75–82 percent and 62–71 percent, with the p-values they print. They also report that vector RAG won on directness, which they treat as a sanity check because directness pulls against comprehensiveness. A claim-count measure agreed with the non-tie LLM labels in 78 percent of comprehensiveness comparisons and about 69–70 percent of diversity comparisons, and those non-tie comparisons were 33 percent and 39 percent of the pairs. Intermediate community summaries sometimes beat source-text summarization by a smaller margin. Root-level summaries used far fewer context tokens. The paper cites Liu et al. on lost-in-the-middle when it chooses an 8k window after finding that window won their size sweep on comprehensiveness.

Those win rates judge generated summaries. They are not retrieval nDCG, and they are not a reason to graph a register that already has specialty, version, effective, and sunset. “Which specialties moved to v4 today” is a feed question. A theme question is the GraphRAG question, and `chk-m03-l03-rag` does not ask it. An extraction prompt over the unfiltered store would also read the staff leaflet and the unauthorized circular. The graph inherits the filter.

## Agentic multi-hop

**Emerging** on multi-hop benchmarks, **Experimental** as the policy citer. Harsh Trivedi, Niranjan Balasubramanian, Tushar Khot, and Ashish Sabharwal, “Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions,” ACL 2023, pages 10014–10037. https://aclanthology.org/2023.acl-long.557/ and https://arxiv.org/abs/2212.10509. IRCoT alternates a chain-of-thought sentence with a retrieval that uses that sentence as the next query. The retrieved paragraphs accumulate until the chain reports an answer or a step limit. They report that, with GPT-3, the method substantially improves retrieval by up to 21 points and downstream question answering by up to 15 points on HotpotQA, 2WikiMultihopQA, MuSiQue, and IIRC, including in out-of-distribution settings and with Flan-T5-large without extra training. “Up to” is their wording. This review does not split those points by dataset.

The design trace lists multi-hop questions. The code has one cite and a `no-document` refusal. IRCoT’s premise fits one unasked Al-Waha question: the in-force endocrinology clause names a preparation code, and the patient must then see the public leaflet with that code. A scripted second lookup does that without a model choosing the hop. An open loop can retrieve `circ-ramadan-unauth` on hop two when the first sentence overlaps that body. Every hop, including a hop the model invented, has to sit inside the audience filter. The wrapper is the lesson. The loop is a later elective.

## Faithfulness metrics, and what they do not see

**Emerging**, with published limits that match this case. Shahul Es, Jithin James, Luis Espinosa-Anke, and Steven Schockaert, “RAGAS: Automated Evaluation of Retrieval Augmented Generation,” EACL 2024 System Demonstrations, pages 150–158. https://aclanthology.org/2024.eacl-demo.16/. The metric docs are https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/faithfulness/. Faithfulness is the fraction of claims an LLM says can be inferred from the retrieved context. The paper also defines answer relevance and context relevance. The context-relevance discussion cites Liu et al. on long context. On WikiEval, which they built from 50 Wikipedia pages about events after the start of 2022, two annotators agreed on about 95 percent of faithfulness and context-relevance labels and about 90 percent of answer-relevance labels. Pairwise agreement between the RAGAS metric and the human preference, their Table 4, is 0.95 for faithfulness, 0.78 for answer relevance, and 0.70 for context relevance. They say context relevance was the hardest, and that the judge model struggled to pick the crucial sentences in longer contexts. They also note that repeating an LLM evaluation is itself unstable when the API moves.

The metric’s definition is support by the retrieved context. A superseded circular quoted accurately scores as faithful. An unauthorized circular quoted accurately scores as faithful. A staff leaflet quoted accurately to a patient scores as faithful if the leaflet was the context. Currency, audience, and version are outside the score. The Alan Turing Institute’s TEA note on RAG evaluation states the same limit in plain language: faithfulness measures whether the answer is supported by the retrieved text, not whether that text is correct, current, or complete, and a system that reports an outdated document accurately scores well. https://alan-turing-institute.github.io/tea-techniques/techniques/retrieval-augmented-generation-evaluation/. That page also recalls the original paper’s 95 percent and 70 percent pairwise figures and the long-context weakness. It adds that claim-by-claim checking can miss a leap across documents when each sentence is locally supported.

Roychowdhury, Soman, Ranjani, Gunda, Chhabra, and Bala, “Evaluation of RAG Metrics for Question Answering in the Telecom Domain,” arXiv:2407.12873, https://arxiv.org/abs/2407.12873, treat RAGAS as a black box and instrument the intermediate claims. They find faithfulness generally concordant with subject-matter experts in their telecom set, and they find that splitting claims can change the score because a simple statement may become several sentences and a complex one may not split. They judge answer similarity, answer relevance, and context relevance less reliable in that domain. The HTML page carries an “ICML” marker this review does not treat as a confirmed proceedings venue. The arXiv identifier is the citation.

Lesson 4’s trap is an uncalibrated judge that marks a fluent wrong citation as correct. Using RAGAS as the grade for Lesson 3 would import that trap one lesson early, and it would bless a citation of `circ-ramadan-unauth` whenever the generated sentence matches the circular. The check this lesson can actually run is extractive: the returned text equals the clause, the clause’s status and audience and version and hash match the bind, and the asker is allowed to see it. That check is **Proven** software testing. RAGAS remains the name a reader should recognize when Lesson 4 introduces a judge, together with the reason a high faithfulness score is not a version check.

## What the sources jointly say about this pack

A code-bearing question wants a lexical rank. A wording-repeat wants a second rank that can be fooled, which the token-share cosine already is. Fusing the ranks is **Proven** and small. Filtering unauthorized, draft, audience, and the wrong version before the fuse is **Proven** and is the part engines still get wrong in public issues. Adding model-written context to each chunk is **Emerging** and aimed at a different failure, on corpora larger than this one. Building an entity graph is **Emerging** for theme questions this check does not ask. Letting a model decide the next query is **Emerging** on Wikipedia multi-hop and **Experimental** here until every hop is inside the pre-filter. Scoring a generated sentence with a second model is **Emerging** evaluation and the wrong grade for a lesson whose next lesson exists to show that judges can be fooled.

The production problems named in the thesis are the ones the primary sources leave open after fusion is solved. Anthropic’s best reported configuration still returns the top 20 chunks into a prompt, which Liu et al. give reason to distrust, and which a staff document must never enter. GraphRAG’s win rates are about summary quality on global questions, after a model has already read the corpus. RAGAS will score a perfect quotation of the wrong version as faithful. None of those results replace `bind.criteria`.

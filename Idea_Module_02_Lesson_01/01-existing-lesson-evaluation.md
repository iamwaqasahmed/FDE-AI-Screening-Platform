# Existing lesson evaluation

Module 2, Lesson 1 is titled Sign-in. The facilitator map calls it “Application shell and sign-in.” The syllabus line is conversational interfaces, authentication, and backend workflows. The objective that the slides, the module page, the understanding map, and the student background all repeat is narrower and accurate: a signed-in patient and a signed-in coordinator can open the assistant. One status question still uses the Module 1 tool. Booking waits. This evaluation holds the lesson to that objective first, then to the larger syllabus line, then to the design notes that describe a delegate and a step-up this release does not grade.

## What the learner actually does

The student copy is nine chapters, `00` through `08`, written for one person who holds five hats. There is no timetable. The case date inside the client chapter is 17 January 2027. The drop is from the enterprise architect, Huda Al-Ghamdi (`ea`). Setup builds `rel-m02-l01` for the `practice` profile and copies the shell into `work/`. The role chapter states the assistant may sign in a patient and a coordinator, may answer status by reading `his-wadi` and then calling the Module 1 status tool, and does not book. There is no interview. The checks do not read an interview note, which the solution trainer chapter confirms.

The client chapter points at three release files and one scenario. `fhir-v2.md` says the hospital record has moved to FHIR v2, that a field from the v1 client is gone, and that booking is a later day. `his-wadi.yaml` is a single OpenAPI 3.0.3 operation, `GET /Referral/{referral_id}`, with one required query parameter, `clinic`. `loa.md` defines `loa-1` as a one-time code that may open the assistant, and `loa-2` as checked against `nid`, required before booking or cancellation. Staff roles are coordinator, contact-center, records, and audit. `svc-integration` is named as a service. `iam.yaml` is not an OpenID Provider metadata document. It is an OpenAPI file with extension fields `x-issuer`, `x-token-endpoint`, and `x-actors` for `patient` (`patient-status`, role patient, `loa-1`) and `coordinator` (`staff-coordinator`, role coordinator, `loa-2`). The words chapter calls that issuer and token endpoint pair “the discovery document.”

Chapters 05 and 06 are transcription. The learner replaces `sprint.md`, `states.md`, and `token-flow.md` by pasting fenced blocks. The sprint says generate the client, sign in both actors, answer status, and leave booking for later. The states table has signed out, a patient at `loa-1` who may ask status, a coordinator who may open the console, and a booking row at `loa-2` marked “Not this day.” The token-flow page says the patient presents a patient token, the coordinator presents a staff token, the assistant does not present `svc-integration`, the session row is written in the application database, and a service token is not a patient token. Chapter 08 pastes `knowledge.md`: “Booking and cancellation require loa-2” and “The session row lives in the application database.”

Chapter 07 is the only engineering action. The learner runs `alwaha.demo.fhir`, which must print exactly `v1 client: his-wadi read failed` and `v2 client: his-wadi read ok`. Then they run `generate.py` against the packet spec. The generator overwrites `work/app/client.py`. Then `run.py` writes `trace.json` and `sessions.db`. Then `server.py` serves the two pages on port 8080. The learner clicks Patient sign-in and Coordinator sign-in. Every other Python file under `work/app` is supposed to stay the packet copy.

The finish chapter runs `chk-auth` and `chk-journey` with `--release rel-m02-l01`. Both must print `passed`. The failure table is honest about what a miss will not reveal: not the role list, not the assurance level, not the removed field, not the status count, not the watermark.

## The generator and the trap

`client.py` in the packet is the trap. `FIELD = "clinicCode"`. `read_body` returns `referral_id` plus that key. `generate.py` does not call an OpenAPI toolchain. `fields()` collects every `- name:` value in file order. `render()` puts the first name into `FIELD` and writes a client that still sends an empty string for that key. `his.py` accepts the read when the body’s keys, aside from `referral_id`, equal the name set from the spec. The value is ignored. A missing spec name fails. A leftover name fails. The engagement module sets `FIELD = "clinic"` and `REMOVED = "clinicCode"`. The old clinic code `END-01` must not appear in the learner pack. The live clinic code `ENDO-CLN` is on the scenario row, not on the OpenAPI parameter list.

The tests lock this pedagogy. `test_m02_l01.py` requires the demo’s two lines, forbids the demo from printing the removed field, the clinic, or `END-01`, and requires lesson notes and templates to avoid `loa-2` and a canary prefix in the README and templates specifically, while the unfinished client must still contain the removed field. `test_generator_matches_the_work_client` requires the solution `client.py` to be exactly what `render()` emits, and every other app module to be byte-identical to the packet. The learner is not meant to design a client. They are meant to run the generator and recognize that the hand-written body no longer matches.

That trap is good integration hygiene. A renamed query parameter is how a versioned HIS actually breaks a pinned client. Hiding the name forces the learner to trust the spec and the demo, which matches the course’s rule that a miss does not leak the secret. The release schedule says `rel-m02-l01` invalidates “a client pinned to FHIR v1 field names.” The traceability note lists “generating contract tests from the spec when `rel-m02-l01` bumps FHIR” as advanced work. The lab stops at generating the client, and the journey check is what fails if the old client remains. The contract-test idea is named for facilitators and not given to the learner.

The naming is the weak point of an otherwise tight trap. The notice says FHIR v2. The words chapter says FHIR is “the record shape `his-wadi` publishes.” The file is a custom referral read. HL7 FHIR does not version itself as v1 and v2. DSTU2, STU3, R4, R4B, and R5 are the published lineage, and SMART App Launch 2.2.0 is written against R4. HL7 v2 is a different standard, which this same module introduces the next lesson as a feed through `int-engine`. A learner who remembers “FHIR v2” on Monday and “HL7 v2” on the feeds lesson has been handed a collision. The Patient resource, normative since FHIR 4.0.0, is demographic identity: identifier, name, active, contact, general practitioner, link to another Patient or RelatedPerson. The Appointment resource describes one planned meeting, with status, participants, and a request path that begins at `proposed`. Neither resource is in `his-wadi.yaml`. The removed field `clinicCode` is not a FHIR element that R4 dropped. It is a local query name.

## What sign-in actually is in the shell

`auth.open_for` refuses `role == "service"` and `sub == "svc-integration"`. A patient with any non-empty `loa` opens chat. A role listed under the staff heading opens the console. Anything else is an empty page, which the server turns into 403. `flow.sign_in` stores `session_id` and `subject` as the token subject, plus `role` and `loa`. `session.py` creates a SQLite table `sessions` with exactly those four columns. An extra column fails `chk-auth`. `server.py` sets `Set-Cookie: alwaha_session={token subject}` with no `HttpOnly`, no `Secure`, and no `SameSite`. The home page offers two buttons. The check also signs in `records` and expects the console, signs in a foreign role and expects refusal, and signs in the service actor and expects refusal. Those messages do not print the list.

`contract.reply` is the product behaviour. A message whose lowercase text contains `book` returns “Booking is a later day,” with `booked` false and an empty tool list. A failed HIS read says the hospital record could not be read. A successful read says the referral is still pending, cites `his-wadi`, and records the tool `status`. Count, state, and facility are copied from the scenario row. `approval` returns status `later`. Health reports `local-small`, prompt version `m02_l01`, and dependencies `his-wadi` and `iam`. The journey check requires all of that, plus two numbered knowledge lines: the first containing `loa-2`, the second containing `database`.

The HIS read itself does not take a caller. `his.read(body, spec)` compares keys. `status_answer` does not pass the session. A patient token and a service token are distinguished at page open, and then the referral read is anonymous with respect to the actor. The design note in `08-live-services.md` describes the confused deputy: an assistant that queries `his-wadi` with `svc-integration` can read any patient, including a canary, and the passing call uses the patient’s token. The shell implements the sign-in half of that sentence. It does not implement the read half. Step-up from `loa-1` to `loa-2` is described there as a foundation-plus check inside `chk-auth`. The eval note says `chk-auth` means “Roles, and a delegate whose grant expired.” The function `auth_problems` grades columns, pages, three refusals, and three markdown files. There is no delegate fixture on this release. The expired-delegate miss string lives in the Module 4 access check. The traceability page lists step-up, delegation, confused deputy, and break-glass as the advanced half of “authentication and backend workflows,” with `chk-auth` as the check. The student finish page calls `chk-auth` partial, and that label is the accurate one.

## Assessment, as implemented

`chk-auth` is a foundation check in the hardness table and a partial check in the lesson map. Both can be true if “partial” means “the foundation slice of authentication that this release owns.” The implementation matches the student failure table, not the hardness table’s delegate clause. A learner can pass authentication for this day by pasting three pages, running a generator they must not edit, and leaving the shell alone. The solution chapter “What done is” lists `auth.py`, `session.py`, `flow.py`, `contract.py`, `chat.py`, `console.py`, `run.py`, and `server.py` as unchanged. The trainer chapter tells the facilitator the staff list, the `records` sign-in, the foreign role, and the service token, and says the check does not print them. That is good secret-keeping. It also means the learner is not asked to implement the rule they are graded on. The rule is already in the packet.

The journey check’s knowledge rule is a substring. Any first numbered line containing `loa-2` and any second line containing `database` passes. The finished sentences are better than the minimum. The minimum is not evidence that the learner can say which NIST assurance family `loa-2` belongs to, or what a session row is for. The states check looks for `patient`, `coordinator`, and `loa-1` in any case. The sprint check looks for the substring `generat` before the substring `book`. These are robust against a little rewording and brittle as measures of understanding. They match a course that wants a green path for a mixed room, including readers who write more than they code. The roles grid gives the lead the FHIR replan, the AI hat the Module 1 tool, the application hat the UI and sessions, the product hat the sign-in states, and the architect the token flow. In the student chapters those five hats are five paste or generate actions, three of which are markdown. The application hat does not change session code. The architect hat does not draw a token exchange. The AI hat does not touch the tool; `contract.py` already calls `status`.

The demo and the watermark rule are the parts a later editor should not loosen. The scenario file carries the profile canary in `letter`. Copying it into `work/` fails `chk-auth` with a watermark message that does not echo the canary. Assistant-use policy forbids the watermark in prompts. The journey miss `his-wadi read failed` does not name a field or a count. Tests assert that. The understanding map says traps are copied so a later editor does not remove them. This trap qualifies.

## Prior knowledge and what the lesson spends it on

The learner arrives from Module 1 Lesson 5 with a scored agent, a design, a readout, and a trace note. Status is a tool. Booking is constrained by approval. Zones put `h-wadi` in `zone-private`. Identity, in Module 1 Lesson 5’s language and again in the data module, means one person stored as two rows. The words chapter explicitly splits that meaning from today’s sign-in file. That split is necessary and easy to lose, because Module 3 Lesson 1 returns to person-level identity. The lesson spends the arrival mostly on a new vocabulary table and a renamed query parameter. The privilege boundary from Module 1 Lesson 4 (a letter must not give away a slot; a tool must not book from a sentence) is preserved by the `book` substring and by `booked: false`. It is not extended to “this token may read this referral.”

The carry-forward sentence, repeated from the solution knowledge chapter into the next lesson’s expected background, is the right size for what was built: a patient and a coordinator can open the assistant, the session row is in the application database, the status question uses the Module 1 tool, booking waited. Tomorrow `eref` pushes `referral.submitted`, and a cancelled clinic session arrives as its own event. The word session is about to change meaning. The token-flow page’s “session row” and Lesson 2’s `session.cancelled` are different objects. The current lesson says this in the understanding map’s new-terms line and does not drill it. A redesign should keep the drill, because the collision is predictable.

## Gaps against the thesis

Measured against integration hygiene, the lesson is complete. The client matches the spec. The old client fails in public. The sprint orders generation before booking. The status path still cites `his-wadi` and does not book. The two user interfaces exist on one process, with compose and a namespace sketch deferred to a later deploy. Tests pin the gold, the canary, the demo text, and the generator output.

Measured against patient-access identity, the lesson introduces the vocabulary and grades the vocabulary. Step-up is a sentence in `loa.md` and a row in `states.md` marked not this day. The shell treats any non-empty `loa` as enough to open chat, so a patient at `loa-1` and a patient at `loa-2` are the same kind of session. Nothing in the check asks for a second factor, an `acr` claim, or a refreshed token before a sensitive action. Delegation is absent. The consent service exists in the live-services design, with grants of view, book, or cancel that expire, and a stale-cache defect switch. This release does not load it. Object-level authorization is absent on the read. The facade is absent: the assistant speaks the HIS dialect directly, and the dialect is labelled FHIR.

The session row is real SQLite, which is the right store for this stage, and the row’s identifier is the subject. Signing in again replaces the row. The cookie value is that same subject. A later reader who treats this as the pattern to copy into the deploy lesson will copy a session design the OWASP session guidance rejects: the identifier should be regenerated at authentication, should carry enough entropy that it is not a username, and the cookie should be `HttpOnly`. The current chapters teach the four column names and the phrase “application database.” They do not teach regeneration, idle timeout, or absolute timeout. For a one-hour paste lab that is a reasonable cut. For the course’s authentication lesson it is the cut that matters.

The five-hat structure is a delivery strength and an assessment weakness. A single reader can finish. A cohort can point at hats. The graded artifacts do not force the architect to distinguish a patient token, a staff token, and a client-credentials token beyond three sentences, and the shell already refuses the third. The product hat’s state table is the right artifact and the wrong evidence, because the table is supplied. The lead’s sprint order is the right priority and is also supplied.

## What should survive a redesign

The hidden-field demo and the rule that failures do not echo secrets. The service token refused at sign-in. The patient kept off the console and the coordinator kept off the chat. The status tool name `status`, with the Module 1 catalogue name `referral.status` recalled in the words chapter. Booking that does not complete, including an approval left at `later`. The watermark. The self-paced chapter order and the single `work/` folder. The knowledge questions as questions: which assurance may book, and where the session row lives. Those questions should be answered from a shell result the learner produced, and the acceptable answer should still be checkable without printing the level on failure. The disambiguation that the next lesson’s cancelled session is a clinic session. The enterprise architect as the source of the notice, including the interview behaviour the tests already lock: the notice turn releases no new fact and does not name the removed field. Students are not asked to run that interview today. Keeping it facilitator-only is consistent.

## What the partial checks are telling the next author

`chk-auth` partial and `chk-journey` status-only are accurate descriptions of the code. They are easy to misread as temporary bugs. They are scope decisions. The journey check on this release does not walk a booking, a cancellation, a webhook, or a caregiver. Later journey checks on `rel-m02-l02` and `rel-m02-l05` widen the same command. The auth check does not grow a delegate in this file. A redesign can extend `auth_problems` and keep the same command, or it can add a new check id. It should not quietly change the pass meaning of today’s green line without a new release note, because later tests import `write_m02_l01` and expect this pack’s gold shape: removed field, live field, roles, booking level, patient level, and the status row.

The evaluation conclusion is that the lesson should stay in the course as the hygiene prefix, and should stop being the course’s authentication lesson. The papers that follow specify the lessons that belong in the gap, the datasets they use, and the failures they are allowed to show.

# Industry research for patient-access sign-in

This paper is a descriptive survey for the Al-Waha lesson. It does not prescribe exploit steps. It marks each source Proven, Emerging, or Experimental using the definitions in the folder README. The course’s invented cluster is a Saudi health system in 2027. The standards below are what a forward-deployed engineer can cite when the hospital record, the identity provider, and the assistant disagree about who is asking.

## SMART on FHIR (Proven)

SMART App Launch 2.2.0 is the HL7 guide for obtaining an OAuth 2.0 access token and a FHIR base URL. The published authorization page requires the authorization-code flow. `response_type` is fixed to `code`. The client sends `client_id`, a pre-registered `redirect_uri`, `scope`, a high-entropy `state` (at least 122 bits; a random UUID is the guide’s example), and `aud`, the FHIR base the token is for, so a genuine token is not sent to a counterfeit resource server. The guide notes that `aud` matches the resource indicator in RFC 8707, and that servers must support `aud`.

PKCE is mandatory (RFC 7636). Servers must support `S256` and must not support `plain`, and must check `code_verifier` at the token endpoint. EHR launch sends the EHR’s `launch` value. Standalone launch omits it and asks the server to establish context, usually with `launch/patient`. A public-client example on the guide requests `launch/patient` together with resource scopes such as `patient/Patient.rs`.

Scopes in version 2 are granular. `patient/Patient.rs` is read and search on Patient in the current patient compartment. `user/*.cruds` is create, read, update, delete, and search on whatever the current user may already access. `system` scopes belong to SMART Backend Services, the client-credentials pattern, and are limited by a pre-configured policy for that client. Version 1 suffixes still appear in the field: `.read` maps to `.rs`, `.write` maps to `.cud`. The guide is explicit that a granted scope is not the underlying permission. A search can return 200 with results omitted. A write can return 403 even when the scope looks broad enough. That sentence is the industry form of the course’s confused-deputy note. A service client with a wide system scope is a different principal from the patient. The patient’s token, bound to a patient launch context, is the principal that should read that patient’s referral.

Discovery for SMART is `.well-known/smart-configuration`, including `authorization_endpoint`, `token_endpoint`, `grant_types_supported` (`authorization_code` and, when backend services are supported, `client_credentials`), and `code_challenge_methods_supported`. OpenID Connect issuer and `jwks_uri` are conditional on the `sso-openid-connect` capability. The course’s `iam.yaml` extension fields `x-issuer` and `x-token-endpoint` are a sketch of the two URLs. They are not this document. SMART 2.2.0 states that it is based on FHIR R4.

The Proven slice for Al-Waha is authorization code plus S256 PKCE, `aud` set to the facade, Patient and Appointment read in the patient compartment, staff OpenID Connect without that compartment, and a backend-services client refused when it is presented as a patient. Finer query-parameter scopes in the same guide are Emerging in hospital portals.

## OAuth 2.0, RFC 9700, and OAuth 2.1

OAuth 2.0 (RFC 6749) is the Proven framework: a client obtains limited access, either on behalf of a resource owner or on its own behalf. Bearer tokens are RFC 6750. The threat-model companion is RFC 6819. In January 2025 the IETF published RFC 9700, Best Current Practice for OAuth 2.0 Security, as BCP 240. It updates the threat model and deprecates modes that field experience showed were weak. It does not replace RFC 6749. It says OAuth 2.1, then in draft, will incorporate these recommendations.

The practices that matter here, at the level of the RFC, are these. Public clients must use PKCE, and confidential clients are recommended to. `S256` is the method that keeps the verifier off the authorization request. Authorization servers must support PKCE and should publish methods in metadata (RFC 8414). Clients must prevent cross-site request forgery on the redirect; PKCE can do that job, and OpenID Connect’s `nonce` does it in OIDC flows. The resource-owner password grant must not be used: it exposes the password to the client and does not fit multi-step authentication. The implicit grant (`response_type=token`) should not be used, because the access token is delivered in the authorization response. Refresh tokens should be sender-constrained or rotated. Redirect URIs should match exactly and should use HTTPS.

OAuth 2.1 is Emerging. The draft fetched for this dossier is `draft-ietf-oauth-v2-1-16`, dated September 2026, expiring 7 March 2027. The abstract says it replaces and obsoletes RFC 6749 and RFC 6750. The draft’s own status says Internet-Drafts are not appropriate to cite as standards. A course that grades learners against OAuth 2.1 section numbers will chase a moving document. The stable grading target is RFC 6749 as constrained by RFC 9700: code flow, PKCE S256, no password grant, no implicit grant, exact redirect match. An advanced reading can say what 2.1 is trying to fold in, and can stop there.

FAPI 2.0 Security Profile is Emerging for this audience and already final at the OpenID Foundation. It follows RFC 9700 and specifies sender-constrained tokens (mutual TLS in RFC 8705, or DPoP in RFC 9449), pushed authorization requests (RFC 9126), and issuer identification (RFC 9207), for confidential clients. A browser chat with a backend holding the token can wait. Booking waits on this release, so FAPI stays a reading until a write crosses a high-value boundary.

## OpenID Connect (Proven)

OpenID Connect Core 1.0 is an identity layer on OAuth 2.0. The ID Token is a JWT with a required `iss`, `sub`, `aud`, `exp`, and `iat`. `sub` is a locally unique, never-reassigned subject at that issuer. It is not a session identifier. The specification says the ID Token’s expiry is unrelated to the lifetime of the authenticated session between the relying party and the provider. That single note separates the course’s current design, where the session id is the subject, from the protocol it believes it is teaching.

`acr` is an optional claim naming the authentication context class that was satisfied. The value `0` means the authentication did not meet the requirements of ISO/IEC 29115. `amr` is an optional list of authentication methods. `auth_time` is required when the client requested `max_age` or asked for `auth_time` as an essential claim. Those three claims are how a relying party expresses step-up without inventing a private integer. A patient who opened the assistant with a one-time code can hold a session whose `acr` is the lower class. A booking attempt asks again, with `max_age=0` or an essential `acr`, and the provider re-authenticates. The new ID Token’s `auth_time` is what the assistant records. The FHIR scopes do not change just because the authenticator changed. Assurance and authorization are different claims.

The course’s discovery shortcut skips the metadata document OpenID Providers publish at a well-known URL, and it skips SMART’s smart-configuration document. A learner who can point at `x-issuer` has not yet fetched `authorization_endpoint`, `token_endpoint`, `jwks_uri`, or `code_challenge_methods_supported`. The proven exercise is to read a local fixture of that JSON, not to stand up a public identity provider.

## NIST SP 800-63-4 and ISO/IEC 29115

NIST Special Publication 800-63-4, Digital Identity Guidelines, July 2025, supersedes SP 800-63-3. It is a Proven US government guideline, not Saudi law, and the course should not present it as either a statute or a certification of Al-Waha. Its value is the split. The relying party selects assurance separately for identity proofing (IAL), authentication (AAL), and federation (FAL). Each scale has three levels. IAL1 fits limited personal-information functions and resistance to synthetic identity. IAL2 fits functions where the user can change consequential details or affect others. IAL3 adds attended proofing and a biometric. AAL1 allows a wide set of single-factor or multi-factor authenticators. AAL2 requires two distinct factors. AAL3 requires a phishing-resistant authenticator. One column named `loa` cannot store “proofed against a national id” and “logged in with a one-time code” together. The course’s `loa-2` (“checked against nid”) is mostly an IAL claim. `loa-1` (“one-time code”) is mostly an AAL claim. Booking needs both a proofing fact and an authentication class strong enough for a change.

ISO/IEC 29115:2013, Entity authentication assurance framework, was confirmed in 2020 and remains the current edition on the ISO catalogue. It is Proven and paywalled. This dossier uses the ISO abstract and the public preview, not a reconstructed clause list. The standard specifies four levels of entity authentication assurance, criteria for each, guidance for mapping other schemes onto the four levels, and guidance for exchanging the result of an authentication. The preview states that the overall level achieved is the level of the weakest phase among the framework’s phases. LoA1 is minimal confidence in the claimed identity, with some confidence the entity is the same across consecutive events, for minimum-risk transactions. It does not require cryptography. LoA2 is some confidence, for moderate risk. Single-factor authentication is acceptable if the entity proves control of the credential through a secure protocol, with controls against eavesdropping, online guessing, and attacks on stored credentials. LoA3 is high confidence, for substantial risk, and requires multifactor authentication, with secrets cryptographically protected in transit. LoA4 is the highest level defined. The preview available here does not carry LoA4’s operational criteria, so the lesson should not invent them. OIDC’s `acr` value `0` is the bridge: a token can say, in a standard claim, that ISO 29115 was not met.

A teaching map stays inside those public statements. A one-time code is an AAL fact and, if the person was only self-asserted, a low IAL. A national identity number presented to an authoritative source is an IAL question, not an authenticator by itself. The app approval, PIN, or biometric used at the same time is an AAL question. The assertion the hospital receives is an FAL question. The cluster’s two bullets can remain local vocabulary if the knowledge file names the family of each bullet and applies the weakest-phase rule. A strong proofing step followed by a bare session cookie does not produce a high overall level.

## Nafath, descriptively (Proven as a national service)

The National Platform describes National Single Sign-On as a Saudi Data and Artificial Intelligence Authority service: one access point for government and private services, for citizens, residents, and visitors, at no charge. The published steps are a verification request in the Nafath application, acceptance of that request, confirmation of the request number against the number on the service’s screen, and entry of the PIN created at login. The SDAIA user guide shows the same number-match path and a second path: national id or Iqama plus the Absher password, then a one-time code to the Absher mobile number. A separate SDAIA guide adds biometric face capture after the number match and the PIN. The National Information Center, linked to SDAIA, lists enhancing digital identity among its tasks.

The pattern is out-of-band confirmation. The relying party shows a number, a trusted app confirms that number, and a PIN completes the event. Face capture is a further step. Absher password plus a one-time code is a different authenticator class from app, number match, PIN, and face. The cluster’s own `iam` mock can take the same shape for a booking step-up: show a code, require a second action, record the class. The course must not call the live service, collect a national id, an Iqama, an Absher password, or a face image, or treat `iam.yaml` as Nafath’s protocol. The official pages describe user steps. They do not publish a student discovery document. The classroom artifact is a local mock with synthetic request numbers. The national service is Proven. The classroom binding is a simulation, Emerging only as a teaching device.

## FHIR Patient, Appointment, and a facade (Proven pattern)

The Patient page on the current HL7 publication is FHIR 5.0.0 and records that Patient has been normative since 4.0.0. The resource is the demographic “who,” maintained by each organization that cares for the person. The same person at many organizations yields many Patient resources. Identifier, active flag, and name are the core elements a facade needs for this lesson. Contact and link point at related people. The security category is Patient. Compartments include Patient, Practitioner, and RelatedPerson. Nationality and similar jurisdictional fields are profiles and extensions, which is why a Saudi national id does not belong in a base Patient example in this course. If a later profile needs an identifier system, it should be a synthetic system URI owned by the fictional cluster.

Appointment, on the same publication line, is one planned meeting. A series is many Appointment resources, or, in R5, a recurrence template that this lesson does not need. The request workflow starts with `status` `proposed` and participants at `needs-action`. Waitlisting is a separate appointment, not a flag on a booked one. The encounter is a different resource and carries the clinical visit. For a lesson where booking waits, the facade may expose Appointment with `proposed` or an empty search. It must not write `booked` from a chat message. R4 is the Proven facade target because SMART App Launch 2.2.0 is based on R4 and because R4 Patient is normative. R5 recurrence and the richer request resource are Experimental relative to this release’s scope. Cite the R4 pages when the lab fixture is authored, and cite the current publication when discussing what “FHIR” means in 2026.

A facade is the Proven integration shape. The HIS keeps its versioned dialect, including the removed field the current trap uses. The assistant speaks FHIR to a stable base. The facade translates. Contract tests pin the facade. The hygiene demo can still show the pinned HIS client failing, while a Patient read on the facade succeeds. A renamed required field is a break. An extra unknown field is a later lesson’s schema-registry topic. The trap stays on the HIS side of the facade.

## Sessions (Proven)

The OWASP Session Management Cheat Sheet treats the session identifier as a secret. It needs at least 64 bits of entropy from a cryptographic generator. Predictable parts reduce that entropy. Exchange it in a cookie, not in the URL. Set `Secure`, `HttpOnly`, and an explicit `SameSite` of `Strict` or `Lax`. Do not put session ids or tokens in web storage. Regenerate the id when privilege changes. Authentication is the main case. Idle timeout and absolute timeout both apply. A high-value clinical session sits in the short idle range the sheet describes.

OpenID Connect’s separation of ID Token expiry from session lifetime matches this model. The assistant stores an independent session id, the subject, the role, the authentication class, `auth_time`, and an expiry. The cookie carries the session id. The subject stays a column. The national id stays out of the row. Regeneration at sign-in and again at step-up is the behaviour to grade. The current row, whose session id is the subject, is the failing fixture.

## Object-level authorization as a defensive test (Proven objective)

OWASP API Security Top 10, 2023 edition, lists broken object level authorization as API1. The weakness is an endpoint that accepts an object identifier and does not check that this caller may act on that object. It is distinct from broken function-level authorization, which is reaching a function the caller’s role should not reach. The patient who may open `/chat` and still must not read another patient’s referral is the first kind. The patient who must not open `/console` is closer to the second, and the current shell already refuses that cross-opening. Comparing a user id from a token to a single parameter is not, by OWASP’s account, a complete fix, because many objects are not owned by a field equal to the subject. A referral id, an Appointment id, and a Consent id need a policy: this subject, this patient compartment, this grant.

The defensive exercise OWASP’s testing guidance supports, and the only form this course should use, is a pair of fixture identities. The test presents patient A’s credential and patient B’s object id, both taken from the pack, and expects a refusal or an empty result. It expects a success when the same credential is paired with patient A’s object. A second case presents the integration client and expects refusal on the patient read. A third case presents a caregiver whose Consent period has ended and expects refusal, then a caregiver whose Consent is in force and expects the scoped read. The lesson text stops at that oracle. It does not ask learners to discover ids, to try sequential values, or to evade a filter. Prevention language stays at OWASP’s level: every function that takes a client-supplied id checks policy; tests cover the mechanism; a change that fails the tests does not ship. Unpredictable ids are a complement, not a substitute, and the teaching bundle can use opaque ids without implying that opacity is the control.

Caregiver access is both a FHIR fact and an OAuth fact. RelatedPerson is the demographic link. Consent is the grant, with a period. A SMART scope does not override an expired Consent. Token exchange (RFC 8693) is an Emerging way to put caregiver and patient in one token. The foundation lab can compare the session subject with the Consent row and leave token exchange for an advanced chapter. Module 4 still grades stale access. Meeting one expired grant on synthetic patients is why the test belongs here.

## What a 2027 cluster engineer should be able to say

A generated HIS client and a FHIR facade are different artifacts. Opening chat is an authentication event at a stated class. A booking attempt is a new event at a higher class, with its own `auth_time`. A Nafath-shaped sign-on is evidence about authenticators and about proofing, which the hospital maps onto its own decision. A service credential is not a patient. Two patient credentials are not interchangeable at an object id. The session id stays out of the subject column. None of those sentences wait on OAuth 2.1 becoming an RFC, and none of them are produced by scanning `- name:` lines.

# 02 — Industry research

Each section states the source, what it actually says, and what it requires of `rel-m02-l05`. Pages were fetched or searched in October 2026. Where the official text is paid or only a vendor restatement, the flag is in the section.

## 1. Strangler fig

**Primary.** Martin Fowler, "Strangler Fig," 22 August 2024, https://martinfowler.com/bliki/StranglerFigApplication.html. This page supersedes the 29 June 2004 post, preserved as "Original Strangler Fig Application," https://martinfowler.com/bliki/OriginalStranglerFigApplication.html. The 2004 text used the title "Strangler Application." Fowler later changed the name because "strangler" was being detached from the fig and read as violence. Teach the 2024 title.

**What the 2024 page says.** A wholesale replacement looks simple because the old behavior seems known. It takes too long, users will not wait, unwanted behavior gets rebuilt, and the cut-over date concentrates the risk. The alternative is gradual: new behavior is added beside the legacy code, then slices of behavior move. Cartwright, Horn, and Lewis name four activities, explicitly not a sequence: understand outcomes, break the problem into parts, deliver the parts, and change the organization so the approach can continue. Seams have to be inserted; legacy systems rarely have them. Transitional architecture, the code that lets old and new coexist and is later thrown away, is often resisted as waste. Fowler's claim is that lower risk and earlier value outweigh that cost. Without an organizational change, the new system repeats the old brittleness. He ties that last point to Conway's law.

**What the 2004 page adds.** The reason to prefer the fig over a cut-over rewrite is reduced risk, steady value, and shorter releases that avoid rebuilding unused behavior. He also says a new system should be shaped so a later fig can attach. "All we are doing is writing tomorrow's legacy software today."

**For this lesson.** `h-wadi` already returns `booked` on the new path. `h-ain` stays on the hospital file. The facility id is the seam. The fig does not grow by giving Ain a slot API on steering day. It grows by accepting Ain into the assistant while the legacy file remains the slot master. Promising a live slot is the cut-over Fowler says goes down in flames: one date, unspecified behavior, and a patient-visible claim the old system has not released.

The queue and the translator are transitional only if an intraday API is a real later seam. Fowler's colleagues, on the Legacy Mimic page below, separate a mimic that will be deleted from an anti-corruption layer that endures because the partner system endures. Ain's file may be that partner. The retro line that leaves "the nightly file" open, as if it were unfinished homework, teaches the file as waste. The readout has to say which it is. For this case the file is the interface.

Activity 4, the organizational change, is the retro's real job: the team stops treating "include the hospital" as "confirm slots the way Wadi does," and it delegates authority for this change model instead of holding a standing review that only hears a pasted note.

## 2. Anti-corruption layer

**Primary for the wording Fowler's site uses.** Ian Cartwright, Rob Horn, and James Lewis, "Legacy Mimic," 12 January 2022, https://martinfowler.com/articles/patterns-legacy-displacement/legacy-mimic.html. Fowler does not have a Bliki page titled Anti-Corruption Layer. A fetch of the mimic article is the primary page on his site that states the pattern. It quotes Eric Evans, *Domain-Driven Design*, and applies the quote.

**Evans, as quoted there.** "Create an isolating layer to provide clients with functionality in terms of their own domain model. The layer talks to the other system through its existing interface, requiring little or no modification to the other system. Internally the layer translates in both directions as necessary between the two models."

**How the mimic article uses it.** A new system that must keep a legacy process alive conforms to the legacy contract. A service-providing mimic implements a legacy interface so old callers notice nothing. A service-consuming mimic calls the legacy interface so the old system notices nothing. Both are transitional. In the logistics example, the partner system that remains outside the modernization gets an anti-corruption layer that is not a mimic, because it will endure. The point of that layer is that the new domain model is not rewritten in the partner's shape.

**Secondary restatement, flagged.** Microsoft, "Anti-Corruption Layer pattern," Azure Architecture Center, https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer. It attributes the pattern to Evans and adds operational consequences: the layer adds latency and a component that must be deployed, monitored, and validated; transaction consistency is the designer's problem; the layer may be permanent or retired after migration. Use this page for the monitoring consequence. Use the mimic article plus Evans for the definition. Do not send students to a gist or a Stack Overflow paraphrase of Evans as the source.

**Bounded context, related primary.** Martin Fowler, "Bounded Context," 15 January 2014, https://martinfowler.com/bliki/BoundedContext.html. Fowler points to Evans for strategic design and for mapping between contexts that use the same words differently. "Clinic code" and "facility id" are that situation. `h-ain` is the cluster's facility. The code inside the nightly file is Ain's.

**For this lesson.** `sched-ain.md` already says the file uses local clinic codes, and chapter 03 tells the student to read the two codes and then forget them. The passing `apply_file` copies the dict through. The cluster model (`queued`, `h-ain`, `zone-private`) never translates the hospital model (`clinic_code`, `status: file`). That is the corruption the pattern exists to stop: the assistant's booking status becomes whatever field the file happened to contain.

The consuming side matches the mimic article. Ain will not grow an intraday API because steering asked. The assistant consumes `POST /files` as Ain already defined it. Little or no modification to the other system. The translation sits in the assistant, in `zone-private`, and the raw file stays in `zone-hospital`.

Two directions, as Evans stated them: file to queue (a known code and a balanced trailer become a still-queued intent, not a booked slot) and queue to file (the nightly drop contains intents the assistant accepted, in Ain's codes). The current lesson implements neither direction. It only chooses a status string.

Microsoft's caveat belongs in the monitoring section. An anti-corruption layer that fails open will book from a file it could not translate. The layer needs its own signal: poison count and translation failures. Those signals are not request rate, error rate, or model latency.

## 3. File transfer, control totals, idempotent reprocessing, poison files

**Primary for the style.** Gregor Hohpe and Bobby Woolf, "File Transfer," *Enterprise Integration Patterns*, public pattern page https://www.enterpriseintegrationpatterns.com/patterns/messaging/FileTransferIntegration.html. The same book's introduction, https://www.enterpriseintegrationpatterns.com/patterns/messaging/Introduction.html, lists four styles. File transfer: one application writes a file that another later reads. The two sides must agree on name, location, format, timing, and who deletes the file. Shared database, remote procedure invocation, and messaging are the other three. The introduction also says messaging is a poor way to move a huge consistent extract, and that FTP of a file is often the practical path when platforms do not share a messaging product.

A second public excerpt of the same pattern, InformIT, https://www.informit.com/articles/article.aspx?p=169483&seqNum=2, states the operational consequence the lesson needs: updates are infrequent, so the systems drift. A customer-address extract produced at night does not stop a bill addressed that afternoon. Freshness is a business decision. The excerpt also lists the work the style pushes onto developers: unique names, a delete policy, a lock or a timing convention so a reader does not consume a half-written file, and an explicit transfer when the disks differ.

**Primary for idempotence.** Hohpe and Woolf, "Idempotent Receiver," https://www.enterpriseintegrationpatterns.com/patterns/messaging/IdempotentReceiver.html. A receiver can see a message more than once even when the sender sent it once. The receiver is designed so a repeat is safe, either by dropping duplicates or by making the operation itself idempotent. Mathematical idempotence is `f(x) = f(f(x))`. For a full nightly file, the second apply of the same file id leaves the same schedule as the first. The current `apply_file` is idempotent only in the trivial sense that replacing an object with an equal object looks the same. A second file that repeats rows without an id would double any counter the team later adds. The lesson never has a counter.

**Primary for a file that must not be applied.** Hohpe and Woolf, "Invalid Message Channel," https://www.enterpriseintegrationpatterns.com/patterns/messaging/InvalidMessageChannel.html. A message the receiver cannot make sense of is moved to a channel reserved for bad messages, so the bad traffic does not clog the good path and so an operator can see it. "Dead Letter Channel," https://www.enterpriseintegrationpatterns.com/patterns/messaging/DeadLetterChannel.html, is the neighboring pattern for a message the transport could not deliver, including after a receive-count limit. Teach both, and keep them apart. A missed night is neither: nothing arrived, so yesterday stands. A file that arrives with a broken trailer is an invalid message: quarantine it, leave yesterday, raise a poison count. A file the transfer dropped on the floor is a dead letter only after the transport has given up. The current shell treats a missing file as "clear the schedule," and the solution treats any arrived object as authoritative. There is no third state.

**Primary for control totals.** Nacha, ACH file details, https://achdevguide.nacha.org/ach-file-details. This is a public layout guide. The operating rules in Nacha's appendix are the fuller authority; the dev guide says so and still publishes the trailer fields. The file header (type 1) carries a file-id modifier that must be unique for a processing day "to allow for thorough duplicate file identification." The batch control (type 8) carries an entry/addenda count, an entry hash, and debit and credit dollar totals. The file control (type 9) carries batch count, block count, entry/addenda count, an entry hash that sums the batch hashes, and the file-level dollar totals. Bank layout sheets restate the same hash rule: sum the receiving routing numbers, keep a fixed width, and ignore overflow out of the high order. Example sheets from processors, such as MUFG's ACH file specifications, match that description. Cite Nacha's page as the pattern source. Cite a bank PDF only as a second witness that the same totals are what production checkers actually enforce. Do not ask students to build an ACH file. The lesson is the idea: a trailer the receiver recomputes, plus an id that makes a resend a no-op.

**Why this is the dominant enterprise interface.** Hohpe and Woolf put file transfer first among the four styles because every enterprise system can write a file. Their bond-trading case drops file transfer only because that desk needs low latency: https://www.enterpriseintegrationpatterns.com/patterns/messaging/BondTradingCaseStudy.html. Ain is the opposite constraint. `sched-ain.md` says the extract is nightly and there is no intraday API. Latency of the model is the wrong chart. Freshness of the file is the chart. The InformIT excerpt's billing example is the patient-visible version: the assistant can tell a patient "queued" all day, and a file applied to yesterday's codes will confirm the wrong clinic if the translator is missing. A team that apologizes for the file and waits for an API will not staff the trailer check. That is the engagement failure.

**For this lesson, the minimum protocol.** A full-file replace, which the course already states as "the last file wins," is safe only with all of the following:

| Rule | Failure it stops | Current grade |
| --- | --- | --- |
| Do not read a file that is still being written (rename or a ready marker) | Partial extract becomes the schedule | Absent |
| Recompute row count and a hash of clinic codes; on mismatch, quarantine | Short file or altered body replaces yesterday | Absent. Any dict wins |
| Same file id applied twice is a no-op | Resend doubles slots or re-sends notices | Absent |
| Unknown clinic code is poison, not a new facility | Hospital-local id leaks into `zone-private` or books the wrong place | Absent. Students must not use the code |
| Missed night retains the previous good file | Empty night wipes clinics | Graded |
| Applied file does not by itself flip a patient to booked | The file is treated as a slot API | Absent. Status `file` is never mapped |

## 4. ITIL 4 change enablement, and CAB theater

**Official public description.** PeopleCert, "ITIL 4 Practitioner: Change Enablement," https://www.peoplecert.org/browse-certifications/it-governance-and-service-management/ITIL-1/itil-4-practitioner-change-enablement-3794. The page's purpose line: maximise the number of successful service and product changes by ensuring that risks have been accurately assessed, authorising changes, and managing change schedules. The same sentence appears on the Axelos certification page for the practitioner module (a `uat2.axelos.com` host in search results; the PeopleCert URL is the stable public one). The Axelos resource-hub link for the practice guide resolved to a shell page with no body, https://www.axelos.com/resource-hub/practice/change-enablement-itil-4-practice-guide. There is no free official HTML of the practice guide on those properties.

**Paid primary, paraphrased and flagged.** AXELOS, *ITIL 4 Practice Guide: Change Enablement*, 22 November 2019. The guide is not republished here. A third-party full-text PDF turned up in search and was not used as a student reading; linking students to a mirrored copy of the paid guide would launder the copyright. The paraphrase below is the standard account of that guide and matches the text search returned from it. Instructors with a PeopleCert subscription should check the sentences against their own PDF before they are printed in a student chapter.

Paraphrase, flagged as coming from that guide rather than from the PeopleCert marketing page:

- Purpose: maximize successful service and product changes by assessing risk, authorizing the change, and managing the schedule.
- The practice is integrated into value streams. It does not try to draw every change in the organization on one board. It balances effectiveness, throughput, compliance, and risk.
- A change authority assesses and authorizes. The authority can be a person or a group, and the change model decides whether authorization is manual, automatic, or skipped.
- A standing change advisory board that meets to clear a pile of changes is described as a common way organizations respond to risk. The guide's criticism is that those boards become bottlenecks, add delay, and cut throughput. Delegation to the team, to a technical expert, or to the product owner is the ordinary path. A formal board is for the change model that needs it, not the default for every change.

**"CAB theater" is not an ITIL term.** It is this packet's label for the failure mode the guide describes, plus the further failure in which the board meets, the change is "approved," and nobody checked a backout or a success test. SysAid's  commentary, https://www.sysaid.com/blog/itsm/know-about-change-enablement, is a vendor blog. It agrees that ITIL 4 stopped treating the CAB as the default. Use it only as a secondary gloss, and only if the practice-guide paraphrase above is flagged next to it. Do not cite it as Axelos.

**How this differs from `cr-ain`.** The course's change request is an authorization to include a hospital and a rule that refusal needs a reason. That second clause is the enablement bias: the practice exists to get changes through, not to run a court. PeopleCert's three obligations are still unmet. Risk is not assessed (the risk is a patient told they have a slot). Authority is "steering," played as five questions, with no model that says who may approve a file-only include. The schedule is four words in `sprint.md`. There is no backout (stop applying, keep the last good file, leave every Ain booking queued). There is no success test (one night whose recomputed trailer matches, and a synthetic book that stays queued).

The steering readout, as pasted, is the theater. The committee hears Smoke, Change, File, Patients, Monitoring, Model, and Asks. Monitoring says the rest arrives later. The change is sequenced. Nobody is asked what happens if the trailer is wrong. A delegated authority with a one-page change record is more ITIL 4 than a longer CAB scene. The lesson should not add a mock committee. It should add the record the committee would be failing to read.

Change models worth teaching in one afternoon, without importing the whole practice:

| Model | Ain example | Authority |
| --- | --- | --- |
| Normal | First inclusion of `h-ain` under `cr-ain` | Named delegate: the FDE, against `sched-ain.md`, after the smoke test. Not a standing board. |
| Standard, later | A nightly apply whose trailer matches and whose file id is new | Pre-authorized by the normal change. No second meeting. |
| Emergency | Not this day | Out of scope. Inventing an emergency path teaches the wrong bypass. |

The course word "change request" can stay as the client's name for the card. The student should learn that the card is the trigger, and the change record is the practice. Using ITIL vocabulary to mean "a ticket titled cr-ain" is the confusion the day currently rehearses.

## 5. Parallel run and reconciliation in hospital cutovers

**What was not found.** No peer-reviewed or official case, in this search, of two live scheduling systems confirming the same clinics for a measured parallel window with a published reconciliation protocol and a clean outcome. A vendor page that recommends 8–14 weeks of parallel financial reconciliation for an Epic-to-ERP migration was rejected as a case study. It is a seller's method, not a hospital's record.

**What the real record supports.** Large EHR cutovers are usually one-way. Teams rehearse, transcribe, and then live on the new system. Dual clinical masters are avoided because a split chart is a safety problem. The failures that get inspected are unmatched interfaces and new systems that confirm or route as if they were already the master. That is the lesson for Ain. A shadow file in the assistant, reconciled and not shown to the patient, is the parallel run that fits. Two bookers that both say `booked` is the harm.

**Case A — VA scheduling implementation. Official.** VA Office of Inspector General, "New Patient Scheduling System Needs Improvement as VA Expands Its Implementation," report 21-00434-233, 10 November 2021, summary https://www.vaoig.gov/reports/review/new-patient-scheduling-system-needs-improvement-va-expands-its-implementation and PDF https://www.vaoig.gov/sites/default/files/reports/2021-11/VAOIG-21-00434-233.pdf. Scheduling went live without the full EHR at Chalmers P. Wylie VA Ambulatory Care Center in Columbus in August 2020, and with the full suite at Mann-Grandstaff VA Medical Center in Spokane in October 2020. The OIG found that VHA and the Office of Electronic Health Record Modernization knew of significant limitations and did not fully resolve them before or after those go-lives. Schedulers built workarounds. Ticket handling did not meet the contract terms the OIG expected the office to oversee. Further deployment was paused in March 2021 for a strategic review. Eight recommendations include scheduler testing, wait-time fields, ticket tracking, a strategy for further issues, audits of scheduling accuracy, and guidance that tells schedulers how to live with limitations until they are fixed.

**Use.** Known limitations shipped, then workarounds became the interface. `cr-ain` that "includes Ain" while the file protocol is untested is the same shape. The OIG's recommendation to test with the people who schedule, and to publish guidance for the limitation, is the product role: the patient at Ain sees queued, and the operator knows what a missed night retains. The March 2021 pause is a backout at program scale. The lesson's backout is smaller and should be written before the first file, not after a harm.

**Case B — VA care coordination after the same go-live. Official.** VA OIG, "Care Coordination Deficiencies after the New Electronic Health Record Go-Live at the Mann-Grandstaff VA Medical Center in Spokane, Washington," report 21-00781-109, 17 March 2022, PDF https://www.vaoig.gov/sites/default/files/reports/2022-03/VAOIG-21-00781-109.pdf. The OIG substantiated scheduling harm after go-live: appointment rows that did not identify the program or location, reminders that omitted place, reminders that sent patients to the building for a telephone visit, and a self-scheduling configuration that let Washington patients book a site in Ohio. Self-scheduling was turned off. Routing designations were still unresolved at review.

**Use.** This is the live-slot trap in a real scheduling system. A new channel confirmed a place the local system did not mean. The remedy on the day of discovery was to disable the confirming channel, not to reconcile two confirmations in front of the patient. For Ain, a synthetic probe that expects `queued` is the disable switch you test before go-live. A notice path that can say `booked` when send fails, which is today's shell, is the Ohio booking: the patient receives a confirmation the master did not make.

**Case C — VA medication lists after the same go-live. Official.** VA OIG, report 21-00656-110, 17 March 2022, PDF https://www.vaoig.gov/sites/default/files/reports/2022-03/VAOIG-21-00656-110.pdf. The OIG substantiated medication-reconciliation failures. Migrated free text carried mapping errors. Staff corrected lists by hand, and the corrections did not stay corrected. The new list omitted discontinued, expired, and clinic medications, so staff still read other systems to see a full list. The OIG states the obvious clinical consequence: an incomplete list feeds the wrong treatment decision.

**Use.** This is an unplanned dual-run. The legacy source was still required, and the new source did not keep a correction. It is not a designed parallel with control totals. Teach it as the reason a shadow reconcile must be explicit: one master, a named second view, and a check that a correction survives the next file. "Last file wins" without a trailer will overwrite a manual correction the same way.

**Case D — Cambridge University Hospitals, Epic, autumn 2014. Journalism, flagged.** Sam Sachdeva, "Testing times for Epic at Cambridge," Digital Health, 25 November 2014, https://www.digitalhealth.net/2014/11/testing-times-for-epic-at-cambridge/. This is trade press summarizing a Cambridgeshire and Peterborough CCG report to the county health committee, plus a trust statement. The CCG PDF was not fetched. Treat the dates and the failure modes as reported, not as a regulator's finding.

As reported: eHospital went live in the early hours of 26 October 2014, the first NHS Epic go-live, inside a program described as about £200 million. On the evening of 1 November the trust declared a major incident, moved Epic to read-only at 23:15, restored it at 02:27, and diverted ambulances for five hours. Pathology results could not be matched reliably to patients; codes and reporting stayed wrong; GPs were asked to stop routine blood tests; some samples were discarded. District-nursing referrals collapsed from about twenty a day to four in five days, and the trust put a paper path in place until the interface worked. The trust's statement said well over 90 percent of the implementation had gone successfully and that patient safety had been put first. A serious incident was reported, and CQC and Monitor were briefed.

**Use.** A core go-live can be "mostly up" while the file-like flows (pathology codes, referrals) are the harm. Paper was the backout for those flows. The assistant's health probe can be green, which is this lesson's smoke test, while Ain's file is unmatched. Cambridge is also the argument against casual dual-running of the clinical record: the trust's immediate technical backout was read-only, not a second live EHR. The paper path was narrow and specific to the broken flow.

**Case E — dress rehearsal, not dual master. Primary deck, limited outcome data.** Boston Medical Center, "An Epic Big Bang," New England Nursing Informatics Consortium, 9 October 2014, https://www.nenic.org/assets/documents/Fall_Winter_Program_Materials/2014%20oct9%20an%20epic%20big%20bang_the%20bmc%20experience.pdf. The deck describes two technical dress rehearsals that walked the cutover timeline, and documentation rehearsals in which nurses and pharmacists practiced typing allergies, orders, and measures from legacy screens into Epic. It does not report a period in which both systems accepted bookings. Use it to show what hospitals rehearse instead of dual live entry. Do not cite it as an outcome study.

**Design rule the cases support.** The assistant may shadow-apply a file and compare counts to queued intents. It may not confirm. Exit from the shadow is a change-record decision after a night whose control totals match and whose synthetic probe stayed queued. Staff guidance for the limitation is part of the change, as in the OIG's eighth recommendation on the scheduling review. Product writes that guidance: the patient sees queued; the operator retains yesterday's file; nobody tells the patient the shadow row is a slot.

## 6. Smoke tests versus synthetic monitoring

**Primary.** Betsy Beyer, Chris Jones, Jennifer Petoff, and Niall Richard Murphy, eds., *Site Reliability Engineering*, "Testing for Reliability," https://sre.google/sre-book/testing-reliability/. Traditional tests check software offline. Production tests hit a live service. Smoke tests are among the simplest system tests: very simple, critical behavior, also called sanity testing, used to short-circuit more expensive testing. Production tests "are in many ways similar to black-box monitoring" in the monitoring chapter, and the book sometimes calls them black-box testing. They are essential to a production service. The chapter's cost ladder matters for a teaching day: a unit test is cheap; standing up a dependency is not. The Ain smoke should stay cheap.

**Primary companion.** The same book, "Monitoring Distributed Systems," https://sre.google/sre-book/monitoring-distributed-systems/. Monitoring is collecting, processing, aggregating, and displaying real-time quantitative data. White-box monitoring reads internals (logs, stats endpoints). Black-box monitoring tests behavior a user can see. The book's paging advice: black-box has the virtue of paging a human only when a symptom is already happening. White-box sees imminent failure and failures hidden by retries. In a stack, one team's symptom is another's cause.

**Secondary, flagged.** Microsoft, "Synthetic Monitoring Tests," Engineering Fundamentals Playbook, https://microsoft.github.io/code-with-engineering-playbook/automated-testing/synthetic-monitoring-tests/. A synthetic monitoring test injects user-like actions with synthetic accounts and checks the effect through the existing monitors. Probes are predictable and are not real-user monitoring. The page lists production risks: bad data, secrets in logs, load, skewed analytics. Google Cloud's product announcement of synthetic monitors, https://cloud.google.com/blog/products/devops-sre/synthetic-monitoring-in-cloud-monitoring-is-now-ga, is a vendor description of scheduled scripts. Prefer the SRE book for the distinction. Use the playbook when the student needs the phrase "synthetic" tied to a probe that books as a fake patient.

**Map onto this lesson.**

| Layer | SRE name | What `rel-m02-l05` does | What the redesign adds |
| --- | --- | --- | --- |
| Unit | Unit test | `test_queue`, `test_file`, `test_notify`, `test_contract`, and only the contract is required | Required cases for trailer, repeat file id, unknown code, missed night |
| Release smoke | Smoke / sanity | `chk-deploy` on yesterday's hash, root, credentials, router | Those, plus one `book("h-ain")` that must return `queued` and must not write `booked` |
| Production probe | Production test, akin to black-box monitoring | Absent. The journey runs in-process | Named, not built: a scheduled probe of the same booking, and a probe that a new file id landed by the cutoff |
| White-box | Metrics from the inside | Request rate, error rate, model latency on the starter dashboard | Named, not built: queue age, poison count, control-break count |
| Symptom worth a page | Black-box symptom | Not defined. "The rest" is the answer | A patient-visible `booked` at Ain, or a night that both missed the file and cleared the schedule |

The starter dashboard is a real white-box of the model service. It is the wrong box for the file. SRE's symptom rule says the page goes to the user-visible failure. For Ain that failure is a confirmed slot or a wiped schedule, not a latency percentile. The release smoke short-circuits the readout: if the synthetic book returns `booked`, steering does not hear a success story. The repeating probe is what Stage 2 still lacks, and the student writes that sentence with the four signal names, not with a module number.

## 7. What the research refuses to add

- A second live slot API "just for the lab." That is the trap.
- A mock CAB with roles and a vote. The practice guide's own criticism is that the meeting becomes the control.
- An ACH parser or an HL7 parser. The Nacha trailer is an analogy. The teaching file stays a small JSON document with `file_id`, rows, and a control object.
- A claim that hospitals routinely dual-run scheduling. The inspected cases do not show that.
- A claim that Fowler wrote a standalone Anti-Corruption Layer bliki. He did not. The mimic article quotes Evans.
